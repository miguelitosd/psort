psort Port Comparison

psort is a utility that reads lines from stdin (or files), counts occurrences, and outputs them sorted by frequency with percentages — the equivalent of sort | uniq -c | sort -n with nicer formatting. The original was written in Perl; ports were made to C, Go, and Python to compare behavior and performance across implementations.

Methodology

Each port was run 100 times on a large input dataset:

/tmp/find.data — 2,289,195 lines of file path data

Timing was collected using /usr/bin/time -f "real=%e user=%U sys=%S mem=%M". Program output was discarded; only the timing metrics were captured.

Metrics collected per run:

  • real — wall-clock elapsed time (seconds)
  • user — user-space CPU time (seconds)
  • sys — kernel/system CPU time (seconds)
  • mem — peak resident memory (%M, kilobytes)

Statistics computed: min, max, mean, and population standard deviation (n=100 runs each).

History: the O(n²) bug and its fix

The original C port used a flat array for counting: every new line triggered a linear scan through all previously-seen keys to find a match — O(n) per line, O(n²) total. On the 107k-line benchmark that went unnoticed (it finished in 0.164s). On 2.3M lines it ran for over four minutes before being killed, and on the 100k–650k scaling benchmark it showed unmistakable quadratic growth, timing out at 650k.

The fix replaced find_entry()'s linear scan with an open-addressing hash table using FNV-1a hashing and dynamic resizing at 65% load factor. Every lookup is now O(1) average, and the C port went from last place (unusable at scale) to first place across all metrics.

Observations

C is now fastest on every metric

With the hash table fixed, psort_c leads on real time (0.519s avg), user CPU (0.460s avg), sys CPU (0.054s avg), and peak memory (67.33 MB avg). No interpreter, no GC, no runtime overhead — just a tight read loop and one hash lookup per line.

Go is a close second — but its GC shows up in sys time

Go's 0.949s real time puts it 83% slower than C but well ahead of the interpreted ports. The standout cost is sys CPU (0.182s avg — 3× more than C or Python), a direct consequence of Go's concurrent garbage collector making write-barrier and heap-scan passes that require kernel interaction. For a task this memory-intensive (2.3M unique strings), GC pressure is the dominant cost above raw computation.

Python beats Perl at scale, and nearly matches Go

Python (1.055s) is only 11% behind Go (0.949s) and 25% faster than Perl (1.402s). CPython's dict implementation scales efficiently to large key counts, and its sys CPU (0.056s) is essentially identical to C — no GC churn. The trade-off is user CPU: the interpreter adds about 0.53s over C's 0.460s. Python also uses the second-least memory (84.55 MB) — less than Go's runtime overhead (100.27 MB).

Perl holds last place at large scale

Perl was competitive on the original 107k-line benchmark but does not scale as well to 2.3M lines. At 1.402s real it is 2.7× slower than C and 33% slower than Perl's closest rival (Python). Perl's hash carries more per-key overhead than Python's dict (135 MB vs 85 MB), which compounds with large unique key counts.

Memory: C now leads, Perl still last

The previous benchmark showed C using ~2 MB on a 100k-line subset (its hash table was then fixed-size). With the dynamic resizing fix, psort_c allocates ~67 MB on the 2.3M-line dataset — the lowest of the four. Python (85 MB) and Go (100 MB) follow. Perl uses 135 MB, roughly twice C's footprint on the same input.

Summary

🏆 Fastest overall: C (psort_c) — 0.519s avg real, lowest user CPU, lowest sys CPU, lowest memory after the O(n²) hash table bug was fixed.

🥇 Second place: Go (psort_go) — 0.949s avg real; fast compiled performance but GC drives sys CPU 3× higher than C or Python.

🥈 Third place: Python (psort.py) — 1.055s avg real; nearly matches Go, beats Perl by 25%, second-lowest memory usage.

🔴 Fourth place: Perl (psort) — 1.402s avg real; competitive at small input sizes but hash overhead accumulates at scale.
